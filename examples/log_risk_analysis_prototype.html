系统的关键设计原则

不让 LLM 直接吃全量日志

LLM 只处理聚合后的证据包：模板、计数、突增、实体、代表样本。

Drain3 前先规范化

timestamp/hostname/severity/source 作为字段，message_core 才进入 Drain3。

按日志源分片建模

kubelet、kernel、containerd、业务 pod 不共用一个模板空间。

风险定位到实体

node/pod/container/ns/ip/volume/device 都要进入实体解析层。

RCA 输出证据链

不是只给“结论”，还要给时间线、相关模板、机器/Pod 拓扑。

Drain3 输出如何被使用

每条日志不再只是一段文本，而变成：
template_hash + template + parameters + entity + window_count + sample_raw

后续分析不再按 raw message 做全文扫描，而是按 template_hash 做：
1. 基线偏离：这个模板在 node-a 上是否突然增加？
2. 首次出现：这个模板是否第一次在该集群出现？
3. 共现关系：kernel OOM 是否先于 kubelet eviction 和 pod reset？
4. 实体归因：模板主要集中在哪台 node / 哪个 namespace / 哪个 pod？

风险评分模型示例

risk(node, 5m) =
  Σ template_weight
  × severity_weight
  × anomaly_score
  × log_count_norm
  × novelty_factor
  × topology_impact

root_candidate 加分：
- kernel/containerd/kubelet 类模板早于 pod 错误
- 单节点集中爆发
- 该节点上多个 namespace/pod 同时异常

LLM RCA 输出示例

10:01:03
内核 OOM 首次出现

node-a 出现 Memory cgroup OOM，属于节点资源压力直接证据。

10:01:04
kubelet eviction 激增

kubelet 开始按 eviction manager 排序驱逐 Pod，说明节点已进入资源回收路径。

10:01:05
业务 Pod 连接重置

pay-api 多个 Pod 出现 connection reset，更像受害现象，不是根因。

RCA 结论 高概率根因为 node-a 内存压力/OOM 导致 kubelet 驱逐和业务连接中断。建议优先检查 node-a 内存水位、异常进程、Pod requests/limits 与近期调度变更。
